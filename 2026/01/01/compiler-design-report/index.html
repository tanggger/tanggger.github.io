一、参考编译器介绍

1.1 参考方案

设计时比较了GCC、LLVM等编译器的架构，最终选择参考 LLVM 的思路。选择 LLVM 主要基于两点考虑：一是其 SSA 形式的中间表示为数据流分析提供了良好的基础，二是模块化的架构便于分阶段实现和后期扩展。

1.2 LLVM 架构分析

LLVM 采用三阶段设计：前端负责词法、语法和语义分析，生成统一的中间表示；中端基于 IR 实施各类优化变换；后端负责目标代码生成。这种分层架构具有以下优势：

  • 前端输出的 IR 采用统一格式，使得优化器无需关注源语言的具体语法细节
  • 中端将优化逻辑封装为独立的 Pass，便于模块化开发与测试，在后期添加新优化时能够快速集成
  • 后端专注于寄存器分配和指令选择，本项目的 MIPS 代码生成部分借鉴了这一思路

1.3 LLVM 接口设计分析

LLVM 各模块间通过清晰的 C++ 类接口进行交互，实现了高度解耦：

前端到中端接口：

  • 数据流向：前端 AST LLVM IR Module。
  • 核心类：LLVMContext (保存全局状态), Module (IR 顶层容器), IRBuilder (指令构建辅助类)。
  • 交互方式：前端遍历 AST，调用 IRBuilder 的方法（如 CreateAdd, CreateBr）向 BasicBlock 中插入指令。

中端优化接口 (参考 Legacy PM 模型)：

  • Pass 架构：所有的优化均继承自 Pass 基类（如 FunctionPass, ModulePass）。
  • 核心方法：子类实现 runOnFunction(Function &F) 或 runOnModule(Module &M) 虚接口来执行优化逻辑。
  • 调度机制：PassManager 维护 Pass 队列，根据 Analysis 的依赖关系自动调度执行顺序。

中端到后端接口：

  • 输入：经过优化的 IR Module。
  • 核心流程：通过 TargetMachine 接口创建 PassManager，注入后端特有的 Pass（指令选择 SelectionDAG、寄存器分配 RegAlloc、栈帧布局等），最终输出汇编文本或对象文件。

Use-Def 链（IR 核心机制）：

  • 继承关系：Instruction 类继承自 User，而 User 继承自 Value。
  • 遍历接口：
    • Value::users()：遍历所有使用该值的地方（Def-Use 链）。
    • User::operands()：遍历该指令用到的所有操作数（Use-Def 链）。
  • 替换接口：Value::replaceAllUsesWith(Value *NewVal) (RAUW)，是实现优化的核心原语。

1.4 LLVM 文件组织分析

LLVM 采用分层的目录结构，各模块职责清晰：

关键设计特点：

  • 头文件分离：接口定义集中在 include/ 目录，便于外部使用
  • 按功能分模块：IR、优化、代码生成分别独立
  • 目标平台隔离：不同架构的后端互不干扰
  • 工具与库分离：核心库在 lib/，命令行工具在 tools/

二、编译器总体设计

2.1 设计目标

本编译器的设计目标是将 SysY 源代码完整编译为 MIPS32 汇编代码。除基本的编译功能外，还需实现错误检查机制以及中端代码优化。

2.2 整体架构

编译流程采用流水线式的阶段划分，各阶段处理完成后将结果传递给下一阶段：

  1. Lexer/Parser：词法分析器生成 Token 流，递归下降解析器根据文法规则构建抽象语法树。这部分实现相对直观，主要按照文法定义进行。
  2. 语义分析和 IR 生成：采用两遍遍历的策略。第一遍进行语义检查（符号定义检查、类型匹配验证等），第二遍生成 LLVM 风格的中间表示。初期曾尝试单遍完成，但发现错误恢复逻辑难以维护，因此改为两遍处理。
  3. 优化器：对中间表示实施常量折叠、死代码删除等优化变换。优化过程具有迭代性，某次优化的结果可能为后续优化创造新的机会。
  4. 后端代码生成：将中间表示翻译为 MIPS 汇编，核心工作是寄存器分配。在实现过程中对分配策略进行了多次调整，逐步提升了寄存器利用率。

三、词法分析设计

3.1 编码前设计

3.1.1 扫描策略

采用向前偷看的线性扫描策略。基本逻辑为：读取首字符后，根据其所属字符类分发至不同的处理函数（如 scanNumber， scanIdentifier 等）。

3.1.3 异常处理预设

针对文法中的非法符号（a 类错误），预设了错误记录机制。当遇到非预期字符（如单独的 &）时，系统将记录当前行号及错误类型，并在内部通过容错逻辑将其暂拟为最接近的合法 Token 继续分析，以避免解析过程中断。

3.2 实现过程中的调整

3.2.1 跨行注释的处理

初始实现中未充分考虑多行注释 /* ... */ 及字符串常量可能跨行的情况。测试时发现行号记录出现偏差，定位到问题后在扫描循环中增加了换行符检测逻辑，每遇到 \n 即更新行号计数器。这一修改虽然简单，但对后续所有错误信息的准确定位至关重要。

3.2.2 关键字识别的优化

最初采用分支结构判断关键字，随着关键字数量增加，代码维护性下降。改为使用 HashMap 存储关键字映射，在扫描到标识符时直接查表判断。这一调整既简化了代码结构，也提升了检索效率。

  1. 单/多字符算子区分：针对 &&、|| 等算子，强化了对不完整输入（如单独的 &）的捕获能力，并将其规整到统一的错误处理流程中。

四、语法分析设计

4.1 编码前设计

4.1.1 解析方案选择

采用递归下降分析法。该方案的优势在于与 EBNF 文法描述高度对应，且便于在解析过程中嵌入 AST 构建逻辑与错误恢复机制。

4.1.3 文法重构：消除左递归

SysY 原始文法中的表达式部分（如 AddExp）存在直接左递归，不符合 LL(1) 预期。

实现中将其改造为：AddExp → MulExp { ('+' | '-') MulExp }。这种迭代式的处理方式在解析时能够正确维持运算符的左结合性。

4.1.5 错误恢复逻辑分析

针对 i/j/k 类（缺少分隔符）错误，Parser 实现了基于虚拟 Token 补全的恢复策略。当 expect 方法检测到缺失符号时，会向 ErrorRecorder 报告行号，并生成一个临时的虚拟 Token 插入解析流，以保障后续节点解析的连续性。

4.2 实现过程中的调整

4.2.1 声明和函数定义的区分

变量声明 int a; 和函数定义 int func() 的开头标记序列相同，单一 Token 偷看无法区分。解决方案是采用多 Token 预读，通过判断标识符后是否为左括号来确定语法类型。这种偷看策略虽然简单，但能有效解决该场景下的歧义问题。

4.2.2 输出格式的调整

测试阶段发现非终结符的输出时机与预期存在偏差。需要逐一调整 logComponent 的插入位置，通过反复测试验证输出顺序。特别是表达式部分，在将左递归改写为迭代形式后，输出时机的把控需要格外注意。

6.2 实现过程中的调整

6.2.1 控制流的 IR 生成

If 和 For 等控制流语句的 IR 生成涉及多个基本块的创建和跳转关系的维护。实现方案是维护一个当前基本块指针，指令生成时插入到当前块中，遇到分支时创建新的基本块并切换上下文。

6.2.2 基本块终止状态检查

在IR生成过程中发现，某些语句(如return、break、continue)会终止当前基本块。如果不检查终止状态就继续向该块插入指令，会导致不可达代码被生成到同一基本块内。解决方案是在每个语句生成前检查 isCurrentBlockTerminated()，如果已终止则跳过后续指令生成。

6.2.3 内建函数的查找机制

在处理 printf 语句时需要调用 putint、putstr 等内建函数。初期实现中未提供统一的内建函数查找接口，导致每次都需要遍历函数列表。改进后增加了 lookupBuiltinFunction 方法，封装了从IrModule中查找内建函数的逻辑。

7.1.3 核心算法

重点预研了基于 SSA 的Mem2Reg算法。设计思路为：首先确定局部变量的支配边界，随后在该位置插入 Phi 节点，最后通过重命名算法消除冗余的内存读写。

支配树算法采用经典的 Lengauer-Tarjan 算法，时间复杂度接近线性。支配边界的计算基于支配树完成，用于确定Phi节点的插入位置。

7.2 实现过程中的调整

7.2.1 优化的迭代执行

初始设计中每个优化 Pass 仅执行一次，但测试发现优化效果不够理想。分析原因是某些优化(如常量折叠)会产生新的死代码，而死代码删除又可能暴露新的优化机会，单次执行无法充分挖掘优化潜力。改进方案是采用迭代执行策略，多轮重复核心优化 Pass。经过实验，5 轮迭代基本可以达到收敛。

7.2.2 编译期函数求值

测试过程中发现部分函数调用在编译期即可完成求值，特别是一些纯计算函数。针对这种情况增加了 Ctfe (Compile-Time Function Evaluation) 优化，在编译阶段直接计算函数返回值。该优化能够有效减少运行时的函数调用开销。
