相对路径+新增指令

实现思路：
内建指令，如 cd 和 exit，因其需要直接修改 Shell 进程自身的状态而被内建；外部指令，如 touch、mkdir 和 rm，则作为独立的可执行程序存在，由 Shell 创建子进程来运行。

1. 内建指令 (Built-in Commands)

cd 与 pwd：当前工作目录管理

这两个指令是相对路径功能的核心。其实现依赖于在内核中为每个进程（struct Env）增加一个指向当前目录文件结构（struct File）的指针 env_cwd。

  • cd 的实现核心：cd 命令的主要工作是解析用户传入的路径参数，并调用一个特定的系统调用（如 chdir）来请求内核更新当前进程的 env_cwd 指针。

  • pwd 的实现核心：pwd 命令则通过一个系统调用（如 getcwd）来从内核获取当前进程 env_cwd 所对应的完整路径字符串，然后将其打印到标准输出。

exit：退出 Shell

exit 必须是内建指令，因为它需要终止的是 Shell 进程本身。其实现非常直接，就是调用 exit() 库函数，该函数会触发系统调用来销毁当前的进程环境。

2. 外部命令 (External Commands)

这些命令作为独立的可执行文件存放在文件系统中。Shell 通过 fork() 和 spawn() 来创建子进程运行它们。这些命令实现的关键在于正确地使用文件系统相关的系统调用，并在执行失败时，从其 main 函数返回一个非零的退出码，以便 Shell 的 && 和 || 能够正确工作。

  • touch 的实现核心：使用 open() 系统调用，并组合使用 O_CREAT（不存在则创建）和 O_EXCL（已存在则报错）标志位，来实现“若文件不存在则创建”的逻辑。如果 open 因为文件已存在而失败（返回 -E_FILE_EXISTS），则将其视为成功（返回 0）。

  • mkdir 的实现核心：

    • 不带 -p 时，直接使用 open() 和 O_MKDIR 标志创建目录。
    • 带 -p 时，需要一个额外的辅助函数。该函数会逐级解析路径字符串（例如，将 /a/b/c 分解为 /a, /a/b, /a/b/c），并对每一级路径尝试调用 open(path, O_MKDIR)，同时忽略“文件已存在”（-E_FILE_EXISTS）的错误，从而实现递归创建。

  • rm 的实现核心：

    • 首先使用 stat() 系统调用来判断目标路径是一个文件还是一个目录。
    • 如果目标是文件，直接调用 remove() 系统调用删除。
    • 如果目标是目录，则检查是否提供了 -r 选项。若没有，则报错“Is a directory”；若有，则进入递归删除流程：打开目录，读取目录下的所有条目，并对每一个条目（除了 . 和 ..）递归地调用 rm -r。

变量和注释

1. 变量的设置、展开与传递

这套机制能够区分对当前 Shell 生效的“局部变量”和能够被子进程继承的“环境变量”，并通过 declare 和 unset 指令进行管理。

  • 变量的存储与管理

    所有变量都存储在主 Shell 进程内存中的一个 struct Variable 数组里。这个结构体不仅记录了变量的键和值，还通过一个 flags 字段来标记其属性（环境变量或只读）。

  • declare 和 unset 指令的实现

    declare 指令用于创建和修改变量，它会解析 -x 和 -r 选项来设置变量的 flags。unset 指令则负责从内存数组中安全地（检查只读属性）移除变量。

  • $ 变量展开与环境变量传递

    在命令执行前，expand_variables 函数会负责将命令中的 $VAR 字符串替换为其实际的值。而在创建子进程时，runcmd 函数会精心挑选出所有被标记为环境变量的变量，并将它们传递给 spawn 系统调用，从而实现环境变量的继承。

2. 注释功能 (#)

实现思路：
注释功能允许用户在命令后添加笔记，Shell 在执行时会自动忽略注释部分。我的实现非常直接，就是在命令执行前的最后一刻，对命令字符串进行处理。

  • 注释的实现核心：
    在 Shell 的主执行循环中，当获取到一条完整的、即将要被送去执行的命令字符串后（此时变量和反引号等已经处理完毕），我会使用 strchr 函数来查找字符串中第一次出现 # 的位置。

指令输入优化和历史指令

1. 指令自由输入与快捷键

这个功能的核心，是将 readline 函数从一个简单的字符读取器，改造成一个迷你的行编辑器。

  • 实现原理：
    我将 readline 设计成一个无限循环，在循环中通过 read(0, &ch, 1) 一次只读取一个字符。我使用一个字符数组 buf[] 来存储当前正在编辑的命令行，一个整型变量 len 记录其长度，另一个整型变量 pos 则作为光标，追踪当前的编辑位置。

    readline 内部通过一个大的 switch (ch) 结构，来判断用户的按键并执行相应操作：

    • 普通字符：通过 memmove 将光标位置（pos）后的所有字符向后移动一位，为新字符腾出空间，然后将新字符插入，并更新 len 和 pos。
    • 退格键 (Backspace)：同样使用 memmove，将光标位置前的字符覆盖掉，实现删除。
    • 快捷键：对于 Ctrl-A (光标到行首) 或 Ctrl-E (光标到行尾) 等快捷键，实现起来相对简单，只需直接修改 pos 的值即可。对于 Ctrl-K (删除到行末) 或 Ctrl-U (删除到行首) 等，则通过字符串操作和 memmove 来实现。
    • 光标移动 (方向键)：方向键会产生特殊的转义序列（如 \x1b[C 代表右箭头）。我的 switch 会先捕捉 \x1b，然后再继续读后续的字符来判断具体是哪个方向键，最终通过增减 pos 的值来实现光标的移动。

  • 屏幕刷新：
    每次按键导致 buf 或 pos 发生变化后，都需要刷新屏幕上的显示。我是通过打印一系列 ANSI 转义序列来完成的：先用 \r 回到行首，用 \x1b[J 清除当前行，然后打印新的 buf 内容，最后再用 \r 和一系列 \x1b[C (光标右移) 将光标精确定位到 pos 所在的新位置。

2. 命令历史 (history 与上下导航)

  • 实现原理：
    命令历史的实现分为内存、文件和用户交互三个部分。

    • 内存存储：我在 Shell 中设置了一个二维字符数组 history_lines[MAX_HISTORY][MAX_CMD_LEN] 作为一个环形缓冲区。history_head 指针用于标记下一次新命令应该插入的位置，history_count 则记录当前有效的历史数量。

    • 持久化存储：Shell 启动时，history_load 函数会尝试打开根目录下的 .mos_history 文件，读取其中的内容来预加载历史记录。当用户执行一条新命令后，history_add 函数会先将其存入内存的环形缓冲区，然后立即将内存中全部的有效历史记录覆盖写入到 .mos_history 文件中，从而实现历史记录的持久化。

    • 上下箭头导航：这部分逻辑实现在 readline 函数处理方向键的 case 中。当检测到上/下箭头时，程序会修改一个用于导航的索引 history_nav_idx，然后从环形缓冲区中取出对应的历史命令字符串，用它覆盖当前的输入缓冲区 buf，并将光标 pos 置于行末。我还特别处理了对用户当前正在输入、但尚未提交的命令的保存和恢复。

3. 不带 .b 后缀执行指令

  • 实现原理： 此功能的核心逻辑被直接实现在了spawn 中。这样一来，所有通过 spawn 启动的程序都能享受到此便利。spawn 的执行逻辑如下：

    1. 首先，它会尝试按用户输入的原样（如 "ls"）去调用 open 打开程序文件。
    2. 如果第一次 open 失败（很可能是因为文件不存在），它并不会立即放弃。
    3. 而是会在一个临时缓冲区中，将原始的程序名和 .b 后缀拼接起来（得到 "ls.b"），然后再次尝试 open 这个新路径。
    4. 如果第二次 open 成功，spawn 就会继续执行这个程序；如果两次尝试都失败了，spawn 才会向上层返回“文件未找到”的错误。

追加重定向、条件执行和反引号

1. 条件执行 (&& 与 ||)

此功能允许用户根据上一条命令的成功或失败，来决定是否执行下一条命令。

  • 实现原理：
    这个功能的实现，完全建立在“基于 IPC 的进程退出状态传递”这一核心机制之上。

    1. 解析：首先，split_conditional 函数会以 && 和 || 为分隔符，将命令行切割成一个 struct Cond 的数组。数组的每个元素都包含一段命令和它后面的连接符类型 (TOKEN_AND 或 TOKEN_OR)。
    2. 循环与短路：在 exec_line 函数中，一个 for 循环负责遍历这个 Cond 数组。在每次循环的开始，它都会检查上一个命令的执行结果 prev_res，并根据连接符类型执行“短路”判断：
      • 如果上一个连接符是 || 且上一条命令成功了 (prev_res == 0)，则 continue 跳过当前命令。
      • 如果上一个连接符是 && 且上一条命令失败了 (prev_res != 0)，则 continue 跳过当前命令。
    3. 获取结果：对于需要执行的外部命令，父进程（Shell）会 fork 一个子进程，然后通过 syscall_ipc_recv() 和 wait() 等待子进程结束，并从 env->env_ipc_value 中获取其退出状态，存入 prev_res，以供下一次循环判断使用。

2. 命令替换 (反引号 `` )

此功能允许将一个命令的输出，作为另一个命令的参数。

  • 实现原理：
    它的核心是利用了操作系统提供的管道（Pipe）和 fork 机制。在 expand_backticks 函数中调用的 capture_command_output 函数是实现此功能的关键，其步骤如下：
    1. 创建管道：父进程（Shell）首先调用 pipe() 创建一个管道，得到一个读取端和写入端。
    2. 创建子进程：父进程 fork() 一个子进程来执行反引号中的命令。
    3. 子进程重定向输出：子进程通过 dup() 系统调用，将自己的标准输出（文件描述符 1）重定向到管道的写入端。然后，它正常执行命令，此时所有本应打印到屏幕的输出，都被写入了管道。
    4. 父进程读取结果：父进程则从管道的读取端不断地 read() 数据，直到管道被关闭，从而将子命令的输出捕获到一个缓冲区中。
    5. 清理：父进程最后还必须调用 syscall_ipc_recv() 和 wait() 来正确地回收子进程，并消费掉子进程附带的 IPC 退出消息，以避免干扰后续主命令的执行。

3. 追加重定向 (>>)

此功能用于将命令的输出追加到文件末尾，而非覆盖。

  • 实现原理：

    1. 识别符号：首先，我修改了 _gettoken 分词器，使其能够将 >> 识别为一个不同于 > 的、独立的新 Token (TOKEN_APPEND)。
    2. 处理 Token：在 parsecmd 函数的 switch 语句中，我为 TOKEN_APPEND 增加了一个新的 case。
    3. 关键实现：其核心技巧分为两步：
      • 调用 open() 打开文件时，使用的标志位是 O_WRONLY | O_CREAT，刻意不使用 O_TRUNC。这保证了如果文件已存在，其内容不会被清空。
      • 文件打开后，在进行 dup() 重定向之前，手动修改文件描述符结构体中的 fd_offset 成员，将其值设置为文件的当前大小 f_file.f_size。这就像手动将“写入光标”移动到了文件的末尾。

挑战性任务难点

1. 复杂的状态管理

  • 进程级状态（CWD）：为实现相对路径，需要深入到内核，修改进程控制块 struct Env，为每个进程增加“当前工作目录”这一状态。这要求在内核与用户态之间建立清晰的界限和交互（通过 cd 和 pwd 的系统调用）。
  • Shell 级状态（变量）：为了实现环境变量和局部变量，需要在 Shell 进程的内存中设计一套完整的变量管理系统。难点在于区分不同变量的作用域（局部 vs 全局）和属性（只读），并设计将环境变量正确地“遗传”给子进程的机制。
  • 持久化状态（历史记录）：history 功能不仅要在内存中实现一个高效的环形缓冲区来管理命令，还要处理与磁盘文件 .mos_history 的同步读写，以实现历史记录的持久化。

2. 底层系统交互与协议设计

  • IPC 退出码协议：这是实现 && 和 || 的基石。由于不能修改内核 wait 机制，我们从零设计了一套基于 IPC 的、可跨越多级进程的退出状态传递协议。难点在于设计 runcmd 作为“中继站”的角色，来保证状态码能从真正的执行者（孙子进程）可靠地传递回主 Shell。
  • 文件描述符（FD）精细操作：实现 >> 追加重定向和 `` 命令替换，都要求对文件描述符有深刻的理解。前者需要通过直接修改 fd_struct->fd_offset 来实现对文件写入位置的精确控制；后者则需要熟练运用 pipe() 创建管道、dup() 复制文件描述符来实现 I/O 流的重定向。

3. 并发与时序问题调试

  • wait() 与 recv() 的竞态条件：这是导致反复死锁的罪魁祸首。我们最终发现，必须先调用 recv() 等待 IPC 消息，再调用 wait() 回收子进程，否则子进程被 wait 清理后，它发出的消息就可能被内核丢弃，导致父进程永久等待。
  • IPC 消息污染：在实现反引号功能时，其子进程发出的 IPC 消息如果没有被及时“消费”，就会残留在主 Shell 的消息队列里，被下一个完全不相关的命令错误地接收，导致后续的 && || 逻辑全盘崩溃。

实验感想

如果说之前的实验是让我们学会如何制造锤子、螺丝刀等“零件”，那么这次的 Shell 项目就是给了我们一张图纸，要求我们用所有这些零件组装出一台能正常运转的“机器”。这个过程让我对操作系统这门课的认识，从“学习理论知识”真正转向了“应用理论解决工程问题”。感谢挑战性任务，感谢os，本学期操作系统课程正式完结！
