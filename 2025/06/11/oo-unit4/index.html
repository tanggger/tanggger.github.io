正向建模与开发

正向建模指的是从高层设计模型开始，逐步细化并生成或指导代码实现的过程。

这个单元的正向建模主要体现在以下几个方面：

需求分析与抽象

首先需要从图书馆管理系统的需求描述开始，分析出系统中的主要实体（如图书、用户、书架、图书馆各部门）及其之间的关系。这对应了面向对象思想中的抽象过程，将现实世界的复杂问题简化为模型中的概念。

UML建模

这个单元指导我们在代码实现之前，通过绘制UML图来指导设计。

  • 类图

    • 类图是通过设计类、属性、方法以及类之间的关系（如关联、继承、实现），来构建系统的静态结构。

    • 类图是正向建模的核心。

  • 状态图
    • 描述了单一对象在其生命周期中可能经历的所有状态以及导致状态转换的事件和条件。
  • 顺序图
    • 展示了对象之间如何通过消息传递或者方法调用来完成特定功能或用例的时序关系。

代码实现以及一致性检查

  • 依据UML图的设计，逐步编写Java代码。
  • 在编写代码过程中，肯定会对最开始设计的UML图进行必要的调整和更新，来保持模型与自己实现的代码同步

架构设计以及代码设计与UML设计的追踪关系

架构设计总结

核心实体

  • BookDetails：表示图书的抽象信息如ISBN、类别、是否热门等。

  • BookCopy：表示具体的图书副本，封装了其唯一的书号、当前位置、借阅/预约状态、日期信息等。

  • Student：表示用户，管理其信用分、当前借阅/阅读/预约状态以及处理各类请求的入口方法。

物理位置

  • Shelf 接口：定义了书架的基本操作（添加、移除、查找、获取所有副本）。其中NormalBookshelf 和 HotBookshelf分别实现了 Shelf 接口，分别管理普通图书和热门图书。
  • BorrowReturnOffice：模拟借还处，负责暂时存放待归还或待整理的图书。
  • AppointmentOffice：模拟预约处，管理被预约并送达的图书副本，并处理逾期预约书。
  • ReadingRoom：模拟阅览室，管理正在被用户阅读的图书。

业务逻辑

  • BorrowLibrarian：处理借书和还书请求，包括各种借阅限制和信用分计算。
  • OrderLibrarian：处理预约和取书请求，包括预约限制和预约书的流转。
  • ReadingLibrarian：处理阅读和阅读归还请求，包括阅读限制。
  • ArrangeLibrarian：负责图书馆的整理工作，包括每日开馆/闭馆时的图书整理和信用分计算。

协调

  • SelfMachine：作为学生与图书馆各项业务处理的代理，将学生的请求分发给相应的 Librarian 类进行处理。这种设计降低了 Student 类与具体 Librarian 类之间的耦合。
  • StudentTable：管理所有学生对象，提供根据ID获取或注册学生的功能。
  • LibrarySystem：整个图书馆系统的入口，负责初始化图书、处理所有输入命令，并协调各个 Librarian 和物理位置对象的工作。

代码设计与UML模型设计之间的追踪关系

类与对象映射

  • UML类图中的“类”，属性，方法，接口均与代码中的一一对应

关系映射

  • 关联：
    • 单向关联: 例如 Student 类持有 SelfMachine 对象的引用 (private SelfMachine selfMachine;)，这在UML类图中会表现为从 Student 到 SelfMachine 的单向关联。
    • 聚合: 表示整体与部分的关系，但部分可以独立存在。
    • 组合: 体现在构造函数中对部分对象的创建和生命周期管理上。
  • 继承：UML中会用实线带空心三角箭头表示，代码中则通过 extends 关键字实现。

行为与状态映射

  • 这一点主要体现在状态图和顺序图。这两类图的概念和作用在上面已经介绍过，这里就不过多赘述。

大模型辅助正向建模

  • 在本次的单元中，我通过使用大模型了解怎么画UML类图，理解关联、聚合、组合等具体的概念以及如何判断类和类之间的具体关系。在生成UML类图的参考代码的时候，大模型没有给出我.mdj的文件代码，而是给了我.puml代码，也就是plantUML的代码。
    个人感觉.puml代码会比.mdj代码更能专注到系统的结构上，而不是一个一个添加属性与方法，而是通过代码的方式来进行类图的绘制。于是，我本单元采取了大模型的建议，先使用plantUML进行初步建模，再根据这个类图进行代码的书写，最后反向优化类图之后才把类图绘制到.mdj文件里面的。

  • 还有就是大模型最后不要用来进行代码整体架构的建立，因为大模型生成架构的时候，经常会不能分清楚用户的需求，会根据用户的一些要求添加一些冗余的一些类，而更难做到在原有给的架构上进行优化，也就是大模型善于“加”东西，而不是“减”东西，最终导致架构的臃肿。

思维演进

架构设计思维的演进

第一单元——层次化设计与初步抽象

设计思路

本单元我的核心思路是String -> Lexer -> Parser -> Poly -> String。但 Poly 类内部（尤其是 Mono）最初可能更多地是基于字符串或简单数据类型（如 HashMap<String, Integer> 表示 x 的幂来存储和操作表达式的不同部分。自定义递归函数部分，我采用的是 token 流的替换，这是一种在文本层面解决递归调用的策略，而非在对象层面进行递归的构建和求值。

设计局限

  • 功能扩展困难：当 Mono 内部的结构（三角函数的参数）本身也是一个“因子”时，原有的简单 HashMap 结构难以直接应对这种递归嵌套。为了合并相同的 Mono，我采取了“递归的比较思路，即若三角函数因子存在的话，就对三角函数里面的因子进行比较，通过逐步比较系数，自变量指数，三角函数相等，从而一直递归到三角函数的因子内部没有三角函数为止，从而结束递归比较”。 这种复杂且需要大量递归比较的逻辑，正是由于内部结构没有被彻底对象化所致。

  • “大类”与职责混淆： Lexer 部分的替换功能性强、代码量较多，导致调试困难。 这表明我的 Lexer 不仅负责词法分析，还承担了复杂的“宏展开”或“替换”逻辑，使得单个方法的职责过于庞大，难以维护。

思维演进
  • 理解了抽象的深化：认识到“因子”内部可以包含更复杂的“表达式”结构。例如，sin(Poly) 中的 Poly 本身就是一个完整的表达式。这意味着 Factor 不再仅仅是 x 或简单的三角函数项，而是一个可以包含其他 Poly 对象的抽象概念。这可以促使思考如何用对象来表示表达式的递归嵌套特性。
  • 组合构建树形结构：自然而然地思考如何通过对象之间的组合关系来表示表达式的层次结构，即构建表达式树。
  • 多态统一行为：理解到对于表达式的各种统一操作（如求导、化简或求值），可以通过多态机制来极大地简化和统一处理逻辑。

第二单元——并发控制与职责分离

设计思路

  • 设计了 InputThread (请求接收)、Schedule (请求分配)、ElevatorThread (电梯运输) 三种线程。

  • 对于涉及共享数据（如请求表 RequestTable）的访问，运用 synchronized 关键字进行同步，对线程安全有了初步的认识，并尝试通过同步机制来管理共享资源的访问，应对多线程环境下的潜在问题。

设计局限
  • 并发安全问题与数据一致性挑战：对共享状态（如乘客请求的接收状态）的并发访问可能会导致不确定的行为。
  • 调试复杂性：多线程环境下非确定性行为对问题定位和复现带来的巨大挑战。
思维演进
  • 线程安全的核心性与深度理解：在多线程环境中，对任何共享资源（如 RequestTable、电梯内部乘客列表、电梯状态、配对电梯状态）的访问都必须通过精确的同步机制来保护，以确保数据的一致性和操作的原子性。

第三单元——契约式编程与高效数据结构选择

设计思路
  • 在第一次接触JML规格时，倾向于直接将JML的描述“翻译”成Java代码。对于对象状态的维护，可能更多地是在方法执行时进行实时计算，而非考虑增量维护或缓存机制。
设计局限
  • 性能瓶颈：仅仅根据JML的功能描述进行直译式的实现，往往无法满足实际的性能要求（如 qts 指令的 O(N) 复杂度）。
思维演进

  • 契约式编程 ：通过JML规格，您深刻理解了软件模块之间（或方法与调用者之间）的契约关系。requires 定义了调用方法的“前提”，ensures 定义了方法执行后的“结果保证”，assignable 明确了方法可以修改的“范围”，signals 则规定了在特定异常条件下的“行为”。

  • 规格与实现分离：JML只定义了“做什么”（功能和行为），而没有规定“怎么做”（具体实现细节）

第四单元——程序架构的设计与抽象以及UML

这一部分上面讲的比较清楚了，就不再赘述了。

测试思维的演进

第一单元

手动构造少量包含各种操作符和嵌套层数的表达式字符串作为输入，然后人工比对程序的输出结果。

第二单元

多线程引入了极大的复杂性，要考虑并发安全和运行时行为，这个单元我使用了评测机来构造极端并发场景（如大量请求瞬间涌入、请求类型高度重复、临界点请求）来进行压力测试。

第三单元

开始掌握规格驱动测试，严格依据JML定义设计单元测试和异常测试，并利用 JUnit 等工具实现自动化。

第四单元

设计能触发复杂规则的数据，并通过日志分析等方法，确保系统在长期运行中的鲁棒性。

课程收获

这个学期的面向对象课终于结束了……就我现在的感觉来说，只有深深的解脱。我认为oo绝对是我到现在以来花时间最长的一门课，我相信后面可能也不会再有来者了。

回想我每周因为oo坐在电脑面前苦思冥想bug到底在哪里，一坐就是五六个小时，意识到的时候已经腰酸背痛的时光；
回想弱测的时候出现WA，点进去看具体样例，发现是一片空白，只能心里暗骂，却又无可奈何，对着代码干瞪眼，不知道从何入手的时光；
回想我第3次作业bug直到周六下午都没有找出来，坐在三号楼手足无措，只能一遍遍点着调试的“下一步”，时不时点开属性页面看能不能对上正确值的时光；
回想我每一次互测拿着评测机，苦思冥想造点造不出来，自己却被人刀了十多刀的时光……我绝对不会说这门课是一门很轻松很有趣的课。

但是，每当我沉浸其中，一步步把要求从抽象的想法变成结构清晰的代码的时候；
每当我检查代码，发现bug，运行样例，惊喜的发现运行出来正确答案的时候；
每当我紧张地点击提交，页面里出现了十个accept的时候；
每当我周日清晨打开互测，不是“很抱歉，你未能成功入围本次互测。我们鼓励你先掌握基础内容，为下一次的互测做准备”，而是显示互测页面，而且看到自己在A房的时候；
每当研讨课上，我不再像以前一样跟别人讨论的时候没有观点，而是能自信的分享自己代码架构，集思广益的时候，我总是觉得，oo这门课也总会给人带来一些小确幸的。

oo，实话说，你真的让我成长了很多，一次次迭代让我构建起面向对象的思想，让我有从容和信心从零开始面对一个项目，一次次研讨课让我也能敢于发表自己的观点，一次次WA磨平了我的锐气和棱角（bushi)。

谢谢你们，oo课的老师们，谢谢你们，oo的助教们，谢谢你，oo。
