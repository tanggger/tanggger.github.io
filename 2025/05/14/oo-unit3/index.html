本单元测试过程

对各类测试的理解与应用

在本单元的社交网络项目中，我们可以应用多种测试方法来保证代码的质量：

单元测试

这是最基础也是最重要的测试环节。它针对程序中的最小可测试单元（通常是类中的一个方法）进行验证，确保其行为符合JML规格的描述。JML的 requires, ensures, assignable, signals 等子句为单元测试用例的设计提供了直接依据。

  • requires 子句：帮助我们构造合法的输入参数和前置条件。

  • ensures 子句：定义了方法执行后期望的返回结果和对象状态，是断言的主要依据。

  • assignable 子句：指明了方法执行过程中哪些对象的状态可以被修改，测试时需要验证未在 assignable 中列出的对象状态是否保持不变 (即副作用控制)。

  • signals 子句：明确了在何种条件下应抛出何种异常。测试时需要构造触发这些条件的情况，并验证是否正确抛出了预期的异常。

功能测试

功能测试关注的是软件作为一个整体或特定功能模块是否满足需求规格说明中定义的功能。在本单元中，这意味着验证整个社交网络系统是否能正确处理指令文件中的各种操作，并产生预期的输出或状态变化。

  • 构造一系列指令，模拟用户在社交网络中的典型操作序列，例如：添加用户 -> 建立关系 -> 发送消息 -> 查询信息 -> 删除表情等。
  • 从输入指令到最终输出（或通过查询方法验证内部状态）进行完整路径的测试。
  • 确保所有JML定义的正常流程和异常流程都能按预期工作。

集成测试

当多个单元（类或模块）组合在一起工作时，集成测试用于发现它们之间接口和交互的问题。在我们的项目中，Network 类是核心，它集成了 Person, Tag, Message 等多个组件。

  • Network 作为集成点：大部分集成测试可以围绕 Network 类展开。

  • 跨类交互：

    • sendMessage (类型0): Message 对象创建 -> Person (sender) isLinked Person (receiver) -> Person 对象的 socialValue, money, messages 列表更新。

    • sendMessage (类型1): Message 对象创建 -> Person (sender) containsTag -> Tag 对象 getPersons -> 多个 Person 对象的 socialValue, money, messages 更新。

压力测试

压力测试评估系统在极端负载（如大量数据、高并发请求——本单元主要是大量数据和指令）下的稳定性和性能表现。目的是找到系统的瓶颈和失效点。

  • 大数据量：构造包含大量用户（如JML中允许的最大数量）、大量关系、大量消息、大量标签的网络。

  • 高频复杂指令：执行大量查询指令（如 qts, qcs, qbs, qsv, dce 等），特别是那些时间复杂度较高的指令。

  • 性能瓶颈识别：通过压力测试，可以发现哪些操作（如 isCircle 的朴素实现、未优化的 queryTripleSum、大量成员的 Tag 的 valueSum 计算等）在数据量大时会超时。

回归测试

当代码发生修改（如bug修复、功能增强、性能优化）后，重新运行之前的测试用例，以确保新的改动没有引入新的错误，或导致原有功能失效。

数据构造策略

基于JML规格的构造

  • 边界值分析

    • 容器大小
    • ID范围
    • 数值范围
    • limit 参数

  • 等价类划分：将输入数据划分为若干个等价类，从每个类中选取代表性数据作为测试用例

  • 异常条件构造：严格按照JML的 signals 子句构造触发异常的数据，如为PersonIdNotFoundException 构造一个不存在的 personId 作为输入，为EqualRelationException 构造两个已存在关系的 id。

基于社交网络特性的构造

图的结构，特殊状态，指令序列的特定组合等等。

如何引导大模型

利用大模型辅助JML规格设计与代码实现时，关键在于有效引导。

核心策略

  • 精准提问与充足上下文：向模型清晰描述你的目标，提供所有相关的JML规格、接口定义、已有的类结构和代码片段。例如，要实现Network.addRelation，需给出PersonInterface、TagInterface以及该方法的完整JML。
  • 任务分解：将复杂任务（如实现整个Network类）分解为小步骤（如实现单个方法，或方法中的某个逻辑分支）。
  • 明确关键约束：在提问时，突出JML中的核心约束（如pure函数不能有副作用，assignable的精确范围）和性能要求。

JML特定场景引导技巧

  • 精确到子句提问，如“\forall 和 \exists 在这里如何理解？”
  • 重点关注JML的副作用（assignable）和契约（ensures, signals），以及\old()表达式的正确处理。
  • 明确指出期望的算法（如DFS/BFS），并提供项目中相关的数据结构和方法（如Person的邻接点获取方式）。
  • 要求模型基于JML的各个条件分支（正常、边界、异常）提出测试场景。

架构设计

整体架构设计

接口层

实体层

  • Person: 代表社交网络中的个体用户。核心数据包括ID、姓名、年龄，以及与其他用户的关系（熟人及其关系值）、拥有的标签、消息列表、社交活跃度、金钱等。
  • Message (及其子类): 代表用户间的交互信息。Message作为基类，封装了消息ID、类型（个人消息/标签消息）、发送者、社交价值等基本信息。子类如 EmojiMessage, ForwardMessage, RedEnvelopeMessage 则在其基础上增加了特定属性（表情ID、文章ID、红包金额）。这是一个典型的继承应用，不同消息类型共享通用属性和行为，同时具有各自特性。

  • Tag: 代表用户标签，可以包含一组用户。核心数据包括标签ID、标签内的用户集合，以及一些统计值。

  • OfficialAccount: 代表公众号实体。核心数据包括所有者ID、公众号ID、名称、关注者列表、发布的文章ID列表以及贡献度信息。

网络管理层

  • 这是整个社交网络的核心控制器和数据中心。它负责管理所有的实体对象（Person, Message, Tag, OfficialAccount），并处理它们之间的复杂交互和查询。

图模型构建与数据结构选择

社交网络本质上是一个图，其中用户是节点 (Node/Vertex)，用户间的关系是边 (Edge)。在本次实验中，我的图模型主要体现在 Person 类和 Network 类中对这些节点和边的管理。

  • 节点 (Person) 的存储：在 Network 类中，使用了 private final HashMap<Integer, Person> people = new HashMap<>(); 来存储所有的 Person 对象。

    • HashMap 提供了 O(1) 的平均时间复杂度来通过用户ID (Integer) 检索 Person 对象。

  • 边 (Relation) 的存储与表示：

    • acquaintance 和 value 两个 ArrayList 通过索引一一对应，可以方便地获取一个人的所有熟人及其对应的关系值。遍历所有熟人时效率尚可。
    • 引入 acquaintanceMap 是一个关键优化。如果没有它，当需要查询特定熟人的 value (如 queryValue(person)) 或者修改/删除特定关系时，需要在 acquaintance 列表中进行线性搜索，时间复杂度为 O(k)（k为熟人数量）。有了 acquaintanceMap，可以通过熟人ID在 O(1) 时间内定位到其在列表中的索引，从而快速访问或修改其关系值，或者在删除时高效地维护列表（尽管删除本身在 ArrayList 中可能涉及元素移动，但定位是快速的）。

  • 标签 (Tag) 与人的关系：

    • Person 类中: private final HashMap<Integer, TagInterface> tags = new HashMap<>(); 存储该用户拥有的所有标签，通过标签ID快速查找。
    • Tag 类中: private final HashSet<PersonInterface> persons = new HashSet<>(); 存储该标签下的所有用户。

  • 消息 (Message) 的管理

  • 公众号 (OfficialAccount) 的管理：

    • 这与 Person 中管理熟人的方式类似，followerIndexMap 用于快速定位关注者在列表中的位置，便于更新贡献度或检查关注状态。

图模型维护策略与性能优化

动态维护图结构及其相关属性是本单元的难点，特别是在需要保证JML规格正确性的同时追求性能。

  • 添加/修改关系 (Network.addRelation, Network.modifyRelation)：

    • Person.bestAcquaintanceDirty = true;：当关系发生变化时，标记“最佳熟人”缓存失效，下次查询时重新计算，这个方法采用的是懒更新。

    • Tag.valueSumCache 的维护：当 addRelation 或 modifyRelation 发生时，涉及到这两个人的标签的 valueSumCache 可能需要更新。我采用的策略是在addRelation 和 modifyRelation时，找出这两个人共同所属的标签，并直接调整这些标签的valueSumCache。

    • Network.tripleSum 的维护：queryTripleSum 是一个典型的需要高效维护的全局状态。

      • JML中的qts指令要求O(N)的复杂度，这意味着不能在查询时实时计算。
      • 在 addRelation(id1, id2, value) 时，遍历 id1 的熟人 p，如果 p 同时也是 id2 的熟人，则形成了一个新的三元组 (id1, id2, p)，tripleSum 增加。modifyRelation 中删除关系时则相反。

  • 查询连通性 (Network.isCircle)：

    • 我使用了 DFS (深度优先搜索)，从一个节点开始DFS，看是否能到达另一个节点。使用 HashSet<Integer> visited 防止重复访问和死循环。

  • 最短路径 (Network.queryShortestPath)：

    • 我使用了 BFS (广度优先搜索)，从起点开始BFS，层层扩展，最先到达终点时的层数即为最短路径长度。使用队列和 visited 集合。

性能瓶颈剖析与优化实践

出现过的性能问题

queryTripleSum 查询效率低下

  • 如果 queryTripleSum 采用暴力遍历所有用户三元组的方式，其复杂度将是 O(N^3) 或 O(N⋅K^2)（N为总人数，K为平均度数），在用户和关系数量较多时极易超时。JML中 qts 指令通常有 O(N) 或类似的性能要求。
  • 修复策略：在 Network 类中维护一个全局变量 tripleSum，当 addRelation(id1, id2, value) 时：遍历 id1 的所有熟人 p，如果 p 也是 id2 的熟人（即 p.isLinked(people.get(id2))），则说明形成了一个新的三元组 (id1, id2, p)，此时 tripleSum 增加。
  • queryTripleSum 变为 O(1) 操作。

Tag.getValueSum() 计算效率低下

  • 如果每次调用 getValueSum 都遍历标签内所有用户对 (P_i,P_j)，并调用 P_i.queryValue(P_j)，复杂度将是 O(M^2⋅K)。
  • 修复策略：在 Tag 类中引入 private int valueSumCache = 0，在addPerson，delPerson，addRelation，modefyRelation方法中进行动态维护。

Person.getBestAcquaintance() 效率

  • 如果每次调用都遍历所有熟人比较value，复杂度为 O(K)。如果此方法被高频调用，会累积不少耗时。
  • 修复策略：缓存与脏位机制。

对规格与实现分离的理解

JML在本单元中扮演了“规格”的角色，而我们的Java代码则是“实现”。我对这两者分离的理解如下：

  • 契约的明确性与稳定性：规格定义了一个方法或一个类的”做什么“，实现关注的是“如何做”。
  • 规格与实现分离的好处：
    • 设计与实现分离：可以先专注于通过JML定义清晰、无歧义的系统行为，而不必过早陷入实现细节。
    • 并行开发与团队协作：一旦规格确定，不同的开发者可以依据规格独立实现不同的模块，或者对同一模块进行不同的实现尝试。
    • 可替换性与可维护性：只要实现严格遵守规格，我们就可以在不影响系统其他部分的前提下，替换掉某个模块的旧实现（比如为了性能优化），或者修改其内部实现细节。

JML规格驱动的JUnit测试设计与一致性检验

如何利用JML规格信息设计JUnit测试

  • 前置条件 (requires) → 构造测试输入：requires定义了方法调用前必须满足的状态。用它来准备合法的测试数据和场景。

  • 后置条件 (ensures) → 验证测试结果：

    • ensures描述了方法成功执行后的预期结果（返回值 \result）和对象状态变化。这是JUnit assert语句的依据。
    • \old(expr)：表示expr在方法执行前的值。测试时需记录旧值，调用方法后用旧值验证ensures中断言。

  • 副作用约束 (assignable / pure) → 检查状态修改范围：

    • assignable列出了方法能修改的状态。测试要验证这些状态按预期改变，且其他无关状态不变。
    • pure方法（即assignable \nothing）不应修改任何状态。测试需验证调用前后对象状态完全一致。

效果

  • 测试直指JML定义的每个细节。
  • JML帮助考虑边界、正常、异常情况，测试更全面。

学习体会

本单元的学习让我深刻体会到JML规格在软件开发中的重要性。通过精确的形式化语言定义接口行为，JML为代码实现提供了清晰的“契约”，减少了理解偏差。初期，阅读和理解复杂的JML表达式，如\forall和\old，确有挑战，但一旦掌握，便能准确把握方法的功能边界和状态变化。

最大的收获在于理解“规格与实现分离”。JML仅定义“做什么”，给予实现“如何做”的极大自由。这促使我不仅要保证功能正确，更要思考数据结构和算法选择以优化性能，如通过增量维护tripleSum和valueSumCache来避免超时。同时，JML也直接指导了JUnit测试用例的设计，特别是针对边界条件和异常情况的测试，有效提升了代码的健壮性。这次经历让我认识到，严谨的规格是构建高质量、可维护软件系统的坚实基础。
